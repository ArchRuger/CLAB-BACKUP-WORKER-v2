COMMON RULES FOR EVERY PAGE SLICE of the "Git save and load redesign" of the Containerlab Node Manager.

Where you work: your own Git worktree (path, branch and base commit are in your assignment). Work ONLY there. Commit on that branch; never push; never touch another branch or the main checkout at /home/archtop/projects/clab-manager. Node tests need no virtual environment: `cd <worktree>/clab-backup-ui && node --test tests/<file>.js`. If you need Python tests: `PATH="/home/archtop/projects/clab-manager/clab-backup-ui/.venv/bin:$PATH" /home/archtop/projects/clab-manager/clab-backup-ui/.venv/bin/python -m unittest discover -s tests -t tests -p <file>`.

One owner per file: your assignment lists the files you own. Edit nothing else. Other slices are building the other scripts at the same time from the same documents. Everything you need from another file is a NAME listed in docs/git-redesign/DESIGN.md section 5 ("Names shared between page scripts"): call it only behind a `typeof name === 'function'` guard at call time, so your file loads alone in a Node `vm` context, and never define a function another slice owns. If you believe a file you do not own must change, do not edit it: put the exact change in your final report.

The documents, in order of authority: docs/git-redesign/DESIGN.md (sections 3, 4, 5 and 7 are binding; "where a part file and this file disagree, this file wins"), docs/git-redesign/REVIEW.md (the answered review findings), then your part file under docs/git-redesign/design/ (the detailed specification: markup, wording, behaviour, tests), then docs/git-redesign/PROMPT.md (the owner's task; Appendix A has the approved markup, and the boards are PNG files in docs/git-redesign/reference/boards/ that you can open with Read). Also binding: CLAUDE.md ("Frontend: three different things", "Browser tests", the invariants) and docs/redesign/DESIGN-SPEC-ADDENDUM.md. Load the skill `clab-manager-ui` before you start.

House rules of the manager UI (binding): plain scripts, no framework, no build step, no CDN; `'use strict'`; dense one-statement-per-line style like the neighbouring files; `esc()` on every interpolation; no inline styles and no `style=` attributes; no listener on `window`, `document`, `location`, `history` or storage outside shell.js; anything re-rendered on the 4 second poll goes through `setMarkup` (or the keyed setter the header design defines) so focus, typed text and ticked boxes survive; every control is keyboard operable; tick boxes are real inputs with labels; colour is never the only signal; wherever a control is disabled the reason is visible text and the action that clears it is beside it; a live region holds only its sentence, never a button. Class names: only those of DESIGN.md 7.5 (HEADER.md 1.3) for shared pieces. Wording: exactly the strings of your part file's wording table and of DESIGN.md; never the words "registration", "prefix" or "overlap"; never "version" where the design says "state".

The two single senders (tests in the owning slices pin them; do not add a second one): `{push: true, reviewed: true}` is sent only by `gitReviewJob` in git-progress.js; `acknowledge: true` to a restore route is sent only by `loadSubmit` in load.js.

Backend contract: DESIGN.md section 4 and 7.4 (routes and shapes) and the public job and lab fields named in DESIGN.md 3 and 7.1 (`note_auto`, `summary`, `captured`, `capture_kept`, `capture_whole`, `kind: 'state'`, `lab.git_status`). The backend is being built at the same time: write against the contract, and in your Node tests answer the routes from a fake `api`/`json` exactly as the contract says.

Tests: `node:test` files that `vm.runInContext` the production script into a context with a fake `$`, `esc` and `state` (copy the harness of tests/test_operations_ui.js for pure functions, tests/test_readiness_ui.js or tests/test_download_ui.js for status.js plus app.js, tests/test_shell_ui.js for shell.js). Every existing test keeps its behavioural claim: a label pinned by an old regex is rewritten, never deleted; a test whose subject an owner decision removes is rewritten to assert the new behaviour, and you list it in your report with the decision (D1 to D10, or the DESIGN.md section) that caused it. New test files must be named in your report (the lead adds them to the CI list).

Before you finish: `node --check` on every script you changed; your test files pass; `node --test tests/*.js` (the whole browser suite) run once, with every failure either fixed (if it is in a file you own) or listed with its cause (if it comes from a file another slice owns); `git diff --check` clean.

Final report to the lead (at most 30 lines unless your assignment says otherwise): branch and commit(s), changed and new paths, each command with its exit status and test totals, the functions you export with their final signatures, every rewritten test with its reason, every name you call that another slice must provide, every place where the documents disagreed or were silent and what you decided, and what is not done.
