### M-1. Manager-side container naming ignores containerlab's `prefix: __lab-name`, so such labs never match discovery

`clab-backup-ui/app/discovery.py:82` · area `vm-clients` · correctness · **CONFIRMED**

**Failure scenario.** A topology with `prefix: __lab-name` is registered or imported. containerlab names its containers `<lab>-<node>`, and host_operations.py `node_selector` documents exactly that. parse_definition (line 82), expected_container (line 209) and reconcile (line 235) build `__lab-name-<lab>-<node>`, which matches nothing in the inspect rows. Every node is marked `absent` with no discovered address, `node_available` is False, and `lab_status` shows 'Partially running' although the containers run. Backups, readiness and SSH stay blocked for that lab. Restart device builds a container name that does not exist on the VM.

**Evidence.** discovery.py:66-67 accepts any identifier as prefix, including `__lab-name`. discovery.py:82 `full = f'{prefix}-{deployed_name}-{short}'`. discovery.py:209 and 235 repeat the same formula. host_operations.py:64 states the `__lab-name` prefix gives `<lab>-<node>`. A grep of tests/*.py for `__lab-name` finds no test and no manager-side handling.

**Suggested fix.** Map the `__lab-name` prefix to `f'{deployed_name}-{short}'` in one shared helper used by parse_definition, expected_container and reconcile. Keep the stored `container_prefix` value unchanged, because stored-data compatibility applies.

**Verifier.** I traced this myself. In discovery.py:66-67 the prefix goes through identifier(), and the regex [A-Za-z0-9_][A-Za-z0-9_.-]* accepts `__lab-name`. discovery.py:82 then builds `__lab-name-<lab>-<node>` as the node name/endpoint, and parsed['prefix'] is stored as container_prefix at discovery.py:833 and vm_files.py:130. reconcile (discovery.py:234-236) builds the same string. Because `expected` is non-empty, the rows.get(node['name']) fallback never runs, so the node becomes discovered=False and runtime_state='absent'. node_available (198-199) is then False, and expected_container (208-209) returns a container name that does not exist. host_operations.py:64-72 documents and accepts `<lab>-<node>` for the `__lab-name` prefix, so the codebase itself acknowledges containerlab's naming. The manager side never maps it, which is a contract mismatch. capture.py:194-198 repeats the same formula, so a capture would target the wrong container as well. The only grep hit for `__lab-name` in app/ is the host_operations docstring; tests/ was not grepped separately (the grep was scoped to app/ plus the repository root). Severity stays medium: the trigger is a deliberate but uncommon topology option, and its effect is that every node of the lab is blocked.

### M-2. Uploading one lab's reviewed save also uploads another lab's unreviewed commits in the same checkout

`clab-backup-ui/app/git_progress.py:1159` · area `git-progress` · security · **CONFIRMED**, reviewer rated it high

**Failure scenario.** Labs A and B are bound to two folder registrations (prefixes 'a' and 'b') of one VM checkout, which the UI supports ('One repository can hold several labs'). Lab B saves: commit CB, job review_pending, not reviewed. Lab A then saves: save() only calls idle(), so it runs, publishes on top of CB and commits CA. The student reviews A: compare shows only CA vs CA^ (folder a), and the 'Uploading also sends N earlier saves' warning counts only lab A's jobs, so it shows nothing. Upload sends retry {push:true, reviewed:true} for A. The helper pushes CA, which carries CB: outgoing {CA, CB} is a subset of known_commits() because _approved_revisions includes every sibling registration of the checkout. Lab B's device configurations, passwords and keys included, reach the remote without B's mandatory review. The manager then leaves B's job at review_pending, because finish() marks synced_operations only for jobs with the same binding_digest. Two other routes do the same thing: (a) a save in lab A that changes nothing returns status 'unchanged' with commit=HEAD=CB (verified); it becomes review_pending, the review shows 'No differences', and the upload pushes CB; (b) a folder move in lab A auto-pushes with want_push=True, and destination() only runs guard_pending(lab_id), which never looks at sibling labs.

**Evidence.** git_progress.py:1159-1163 (retry checks only this job's own reviewed flag); git_progress.py:716-724 and 733 (unchanged handling; sync marking limited to the same binding_digest); git_progress.py:983 and 1001-1008 (guard_pending(lab_id) only, then the move is queued with want_push=True); host_git.py:1116 (_approved_revisions = every registration with the same path, push_url, branch and uid); host_git.py:390-400 and 457-458 (outgoing commits are accepted when they are in known_commits under any approved revision); host_git.py:633-636 (unchanged result reuses HEAD, verified when HEAD is a sibling's commit); git-progress.js:635 ('others' is filtered to job.lab_id).

**Suggested fix.** Before any push (retry with push, the move's want_push, an unchanged save whose commit is not this job's own), refuse while a lab bound to the same checkout (same repository path and push_url) has a pending unpushed, unreviewed commit. Alternatively, have the helper accept in a push's outgoing set only commits whose journals carry this binding's own revision (or that the manager names as reviewed). Also extend the review dialog's 'earlier saves' count to sibling labs of the same checkout.

**Verifier.** I traced the scenario through the code and it happens as described. save() (git_progress.py:1064) only calls idle(). idle() (551-554) blocks on GIT_BUSY statuses ('queued','capturing','exporting','pushing', lab_operations.py:27), and review_pending is not one of them. Nothing in save() looks at sibling labs' pending saves. publish (host_git.py:570-571) takes HEAD=CB as expected_head and commits CA on top of it. Commits are journaled with verified=True at commit time (host_git.py:523). main() fills _approved_revisions with every registration that shares path, push_url, branch and uid (host_git.py:1116), so CB's journal is in known_commits() (390-400). push() therefore accepts outgoing {CA, CB} (457-458) and pushes both. retry() (git_progress.py:1159-1163) checks only this job's own reviewed flag. finish() marks synced only jobs with the same binding_digest (732-735), so B's job stays review_pending. The two other routes also hold. (a) An unchanged publish sets commit=head and verified=head in known_commits() (host_git.py:633), which is true for a sibling's CB. finish() then finds no pushed job with the same binding_digest (716-719), so the job becomes review_pending, and the upload pushes CB through retry_push. (b) destination() runs only guard_pending(lab_id) (983), and the move job carries want_push=True (1007), so the push at 605-607 carries sibling commits. Several labs in one repository is a documented, supported layout (docs/GIT-PROGRESS.md:199-204). The '1.30.6' changelog documents that earlier saves 'go along' only for the same lab, and the dialog counts only gitLabJobs(job.lab_id) (git-progress.js:635). This breaks the CLAUDE.md invariant that a review before every upload is mandatory. I rate it medium rather than high: the commits only reach the remote that lab B's own binding already targets, the same no-login student made them, and they were committed for that remote.

### M-3. Changing a lab's folder retires the old VM registration before validating; a later refusal leaves the lab bound to a registration that no longer exists

`clab-backup-ui/app/git_progress.py:995` · area `git-progress` · correctness · **CONFIRMED**

**Failure scenario.** A lab's topology lost a device after it was bound (a discovery sync removed it), so binding['node_names'] holds a name that is no longer a supported node. The student picks a new folder: POST /git/destination. The route calls register-prefix with retire=True, and the VM deletes the lab's current registration from git.json. bind_lab() then refuses with 400 'Select distinct supported devices from this lab.' The same happens if idle() or guard_pending() now fails because a backup or discovery import started during the helper round-trips, if the VM connection changed, or if the status call fails. The lab's stored git_binding still names the retired binding_id, so every later status, save, history and compare fails with 'Select a registered Git repository.' remember_folders() is never reached, so an empty old folder also disappears from the folder list.

**Evidence.** git_progress.py:981-997 (only idle, guard_pending and host identity are checked before the irreversible register-prefix with 'retire': True); git_progress.py:850-871 (bind_lab re-runs the status call, idle, guard_pending, host identity and the node_names subset check only after that); host_git.py:1059-1062 (retire removes the source registration and writes the registry).

**Suggested fix.** Run every check bind_lab performs (node_names still a subset of the supported nodes, no other lab bound to the target) before sending register-prefix with retire. Better, register the new prefix without retire, bind the lab, and only then retire the old registration in a follow-up call, so a refusal leaves the old registration in place.

**Verifier.** destination() (git_progress.py:979-997) checks only idle(), guard_pending(lab_id), host identity, prefix != source, the snapshot-folder conflict and the other-lab folder conflict before it calls register-prefix with retire=True (995). On the helper side, register_prefix (host_git.py:1059-1062) deletes the source registration and writes the registry. bind_lab (850-871) then runs the live status call, idle(), guard_pending(), host identity and the node_names subset check; any of these can raise. The node_names subset is never checked before the retire. node_names are never updated when nodes change: git_binding is written only by bind_lab, link and unlink. save() itself refuses when names are not a subset of the supported nodes (1069), so the stale-device state is real. After the refusal the lab's git_binding still names the retired binding_id. Every later helper call returns 'Select a registered Git repository.' (host_git.py:1113-1114), and a second destination() fails in plan_prefix because the source is gone (host_git.py:986-987). remember_folders (999) is skipped. The impact is limited: guard_pending ensures no pending save exists, so no saved data is lost, and the student can re-link through PUT /git or connect to the new registration, which exists. The race cases (a backup starting or the VM connection changing between the helper round-trips) depend on timing, but the ordering defect itself is deterministic in code.

### M-5. A shutdown during the post-restart recheck finalizes the job as "Checked" although the node was never read back

`clab-backup-ui/app/restore.py:1085` · area `restore` · correctness · **CONFIRMED**

**Failure scenario.** The manager restarts while an IOS XR target is in 'confirming'. The held arming session is lost, so after the restart pending() returns True (not held) and _settle() keeps polling every 10 s until the trial runs out. If the manager is stopped again during that wait (an upgrade, a compose restart), stopping.wait() returns True and _settle returns ('stopping', {}). _record_settled() returns without writing, so the target keeps status 'interrupted' ('The manager is checking what is active on it now.'). The finally block still decrements rechecks and calls _finalize(prefix='Checked after a manager restart. '). For a one-node job that gives status 'failed' and the message 'Checked after a manager restart. No node was restored...'. The job is no longer in RESTORE_BUSY and is no longer 'interrupted', so the next start never rechecks it. If the change had in fact been confirmed before the first restart, the device runs the saved configuration while the job says no node was restored, and nothing was read back.

**Evidence.** restore.py:1073-1075: _settle can return 'stopping' (restore.py:1012-1015), and _record_settled returns at once for it (1018-1019). restore.py:1085-1094: the finally block always decrements self.rechecks and calls _finalize when the count reaches 0. _finalize (1134-1159) counts the remaining 'interrupted' target as `bad` and pops `_candidates`. __init__ (254-268) only revisits jobs whose status is in RESTORE_BUSY, so the finalized job is never rechecked. The execute path handles 'stopping' correctly (restore.py:786-787 returns early), but this restart path does not. No test covers stopping during _recheck_interrupted (the tests at test_restore.py:1095 and 1418 cover only the execute path).

**Suggested fix.** In _recheck_interrupted, when state == 'stopping' (or the target is still 'interrupted' or IN_FLIGHT), do not count it as rechecked and do not finalize. Return before the finally's decrement-and-finalize, and leave the job 'interrupted' with the target still marked for recheck so the next start() picks it up (see the next finding).

**Verifier.** I traced this in restore.py. _settle returns ('stopping', {}) when stopping.wait() fires (1012-1015). _recheck_interrupted passes that to _record_settled, which returns at once for 'stopping' (1018-1019), so the target keeps status 'interrupted'. The finally block (1085-1094) still decrements self.rechecks and calls _finalize(prefix='Checked after a manager restart. ') once the count reaches 0. _finalize (1134-1165) counts 'interrupted' as bad. For one node it gets verified=0, restored=0 and needs_review=0, so the job becomes status 'failed' with 'No node was restored...', and _candidates is popped. Shutdown cannot stop this write: close() only sets stopping and shuts the pools down (298-303), and the store stays usable during lifespan teardown (main.py:65-74). The next __init__ revisits only RESTORE_BUSY jobs (256), so the 'failed' job is never rechecked. The execute path does avoid this with the early return at 786-787. The failure needs a second graceful stop during the recheck wait, which can last up to the confirm window plus 90 s (for example IOS XR without its held session). The damage is a false 'not restored' report with no read-back, not a change on the device, so I rate it medium.

### M-6. _resolve_pending ignores IOS XR typed negations, so an applied XR change is always judged absent and its statements are dropped from the ledger

`clab-backup-ui/app/design_apply.py:563` · area `design-apply` · correctness · **CONFIRMED**

**Failure scenario.** An apply on an XRv9k ends 'uncertain', for example because the fresh connection failed until deadline + grace after the held session's commit went through. The plan configures interfaces with 'no shutdown' and 'lldp > no management enable', as netlab's XR fragments do. _record_uncertain stores pending.desired = the review's desired set, and on XR that set holds the target buffer's typed negations ('interface Gi0/0/0/0 > no shutdown'). The ledger keeps owned & after and drops pending.added, and the event says 'the change is not there; nothing is owned from it'. From then on the manager's own XR statements are unowned. Dropping the module removes nothing and still reads back 'verified' while the config stays on the router. A changed link prefix reports the manager's old address as a manual conflict that needs a take-over.

**Evidence.** design_apply.py:562-566: desired = set(pend['desired']); present = bool(desired) and desired <= after. The settle path handles the same case correctly at design_apply.py:785-786 (present, absent = own.split_negations(kind, desired); present <= after and not (absent & after)), as does verify() at design_ownership.py:270. design_ownership.split_negations (249-261) documents that XR's desired set carries negations the running config never shows (live fact, XRv9k 24.3.1; PROVISIONING.md §8 'IOS XR negations'). test_design_ownership.py:268-270 pins that 'no shutdown' is never in after. No test covers _resolve_pending on cisco_xrv9k: test_design_apply.py:1025 uses cEOS only.

**Suggested fix.** In _resolve_pending use the same test as the settle loop: present_set, absent_set = own.split_negations(kind, desired); present = bool(desired) and present_set <= after and not (absent_set & after). Add an XR case to test_design_apply.py next to test_a_pending_entry_whose_change_is_present_becomes_owned_at_the_next_review.

**Verifier.** I checked this against the code. design_apply.py:562-563 computes `present = bool(desired) and desired <= after` on the raw pending desired set. On XR that set is `_desired` from the review: statements(rendered) - statements(clean) at line 513, taken from the target buffer. design_ownership.split_negations (249-261) says that buffer echoes typed negations ('no shutdown', 'no management enable') which running-config never shows. test_design_ownership.py:267-270 pins that `after` lacks 'interface Loopback0 > no shutdown'. Only test_design_apply.py:1025 covers _resolve_pending, and it uses cEOS. Trigger requires an XR 'uncertain' outcome first.

### M-9. Same-origin guard compares Origin with the Host-derived base_url, so DNS rebinding bypasses it

`clab-backup-ui/app/main.py:103` · area `core` · security · **CONFIRMED**, reviewer rated it high

**Failure scenario.** A student with the manager open on the lab network visits http://attacker.example:8081. The attacker's DNS then rebinds attacker.example to the VM's private IP (the default bind is 0.0.0.0:8081 with host networking). The page's fetch('/api/...') then arrives with Host: attacker.example:8081, Origin: http://attacker.example:8081 and Sec-Fetch-Site: same-origin. str(request.base_url) is built from that Host header, so origin == base_url and the guard lets the request through. The attacker page can then read /api/state and download every backup ZIP (GET /api/jobs/{id}/download, full device configurations with their secrets). It can also POST deploy/destroy previews and confirms, remove labs, run restores and get terminal tickets: the WebSocket Origin checks in node_services.py:248-250 and capture_sessions.py:194-196 also compare against the request's own Host (ws.url.netloc). Recent Chrome's local-network permission prompt reduces the exposure on Chrome only; Firefox and Safari are fully exposed.

**Evidence.** main.py:101-104: the only check is sec-fetch-site != 'cross-site' and origin == str(request.base_url).
