# Parity review — module `git-places-restore` (folder browser `git-places.js` + live configuration restore `restore.js`)

Inputs read in full: the user brief, `DESIGN-SPEC.md` (224 lines), `UX-AUDIT.md`, `inventory/git-places-restore.md` and the inventory agent's structured output (35 capabilities, 7 dialogs, 31 microcopy issues), `tests.md` §6/§11/§14, `css.md` §20, `git-progress.md` §7.3/7.4/7.8/§10, the two source files, `git-progress.js` 55-175 and 280-320, and backend routes `history`/`version`/`compare` in `app/git_progress.py` plus `restore_jobs` in `app/main.py`. Screenshots viewed: `02-tab-git`, `06b-git-load-dialog`, `04-git-save-menu` (1920×1080).

Backend facts that decide several rows (verified, not assumed):
- `GET /labs/{id}/git/history` returns versions `{label, path, commit}` only; `restore_supported` is computed solely by `POST /labs/{id}/git/version`. The folder browser derives `restorable` client-side from the `/tree` file list (`latest/*.jcfg`).
- `POST /labs/{id}/git/compare {commit,path}` diffs that version against **this lab's `latest/` at HEAD** (the last save), never against the running routers.
- `/api/state` carries `restore_jobs` (last 200, with `lab_id`, `status`, `targets`), so a banner or list can re-open `restoreShowJob(id)` (which fetches when `known` is omitted).

Change vocabulary: `unchanged` (same place, mechanics and label; copy may be rewritten), `moved`, `renamed`, `moved+renamed`, `reorganized` (entry points or layout re-cut), `behaviour-changed` (the spec as written would alter gating or a working flow), `UNMAPPED` (the spec gives it no home).
