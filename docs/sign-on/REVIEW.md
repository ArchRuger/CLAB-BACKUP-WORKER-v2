# Sign-on and exposure hardening: design review

The Opus review of [DESIGN.md](DESIGN.md), [UI.md](UI.md) and [EXPOSURE.md](EXPOSURE.md) after the
rulings of [RECONCILIATION.md](RECONCILIATION.md) were applied to them, with the lead's answer to each
finding. A finding is closed only by a change to the design or by a stated reason. Both reviewers were
read-only and ran no code; every answer below is a decision, and the code that implements it is tested
in the build ([BUILD.md](BUILD.md)). Written 2026-11-01 by the lead of the second session, against the
documents at commit `7d871bc`.

## 0. How the review ran

1. **Attack.** `risk-reviewer` (privilege, persistence, concurrency, deletions, the VM boundary) and
   `clab-ui-reviewer` (the interaction as the person sees it, lost functionality, wording) read the three
   documents and the code they must fit, in parallel, through the project workflow
   `/clab-design-review`. The risk reviewer returned 23 findings (2 must-fix), the UI reviewer 17 (3
   must-fix). Eight UI findings repeat a risk finding and were merged into it (U1→R1, U2→R2, U3→R13,
   U6→R14, U10→R10, U12→R11, U14→R5, U17→R12); R23 is the risk reviewer's "areas checked, nothing found"
   and is not a finding.
2. **Verify.** Every remaining finding (31) went to two Opus refuters, one asking whether the claim is
   true of the text and the code, one whether it is material, each told to refute when it could not
   confirm from the files. A finding falls when either refuter refutes it. The two refuters per finding
   ran in six parallel workflows of the same shape as `/clab-design-review` (the machine's four CPUs cap
   one workflow at two agents at a time). **30 stand, 1 falls (U16, section 4).** Several refuters ran
   their own scratch experiments: R7 (a burst of 120 sign-ins held all 40 worker-thread tokens and
   `/api/state` took 1.9 s), R22 (the guard's `request.state.user['name']` on a sign-in without a session
   is a 500), U8 (the Load watch re-arms itself from the render path every 1.5 s after a 401), U16 (the
   current `api()` fed the gate's bodies).
3. **Answer.** The lead's answers are below; the refuters' corrections are folded into them. Section 5
   says where each answer lands in the three documents.

What the risk reviewer confirmed (R23): no privilege widens on the VM boundary. The gateway, the helper
whitelists, the trusted roots and the pinned host key are unchanged; `PUT /api/host` (which also holds the
host-key reset) becomes admin-only; Git still runs as the registered owner; restore and design-apply
transactions run on the server and do not depend on a browser session, so a sign-out cannot interrupt a
timed confirmation; every container lookup in the deploy scripts names the `backup-ui` service, so none
picks up the new redirect container.

## 1. Must-fix

| ID | Finding | Answer |
|---|---|---|
| R1 (+U1, L1) | A user who must change their password loops between `/` and `/login?change=1` and never reaches a change form: `GET /login` answers `302 /` to any live session, UI.md builds no `/login?change=1` view, and its index.html dialog needs `/api/state`, which a restricted session cannot read. Every user an admin creates or resets is affected. The lead's own finding while drawing the boards (L1): the required dialog had no way out, not even sign-out. | **Accepted: the forced change lives on the sign-in page.** A restricted session keeps the minimal allowlist (the exempt rows, `GET`/`DELETE /api/session`, `POST /api/session/password`). `GET /login` *serves* the page to a restricted session; only an unrestricted session gets `302 /`. Any other page request of a restricted session answers `302 /login?change=1&next=<path>`; any other request (an `/api/` route, a static file) `403 {detail:{code:'password_change_required', message}}`; a socket closes 1008 `password_change_required`. `login.js` shows a change view in the same card (`#signin-change`) when `POST /api/session` answers `must_change_password: true`, or on load when `GET /api/session` says so: *Choose your own password* / *The password you signed in with was set by an administrator. Choose your own before you continue.*, New password and New password again with the policy help, **Change password and continue**, and **Sign out** (`DELETE /api/session`, then the sign-in form; L1). The current password is taken from this page load's sign-in form; after a reload the view shows its own *Current password* field. Success → `location.replace(next)`. UI.md 6.3's index.html required dialog is removed: a live session never becomes restricted (the flag is set only when an admin creates a user or resets a password, and a reset ends every session of that user). Test: sign in as a new user, follow every redirect to a final 200, change the password, land on `next`. |
| R2 (+U2) | `signin.failed` and `signin.throttled` record the submitted name as the actor; a password typed into the username field (a common slip, and the form lowercases it) is written to `audit.jsonl` and shown to admins. UI.md said `actor: null` for unknown names; the documents disagreed. | **Accepted.** The actor of a failed or throttled sign-in, and of `setup.failed`, is the submitted name **only when it equals an existing record's name**; otherwise `-`. No log, response or detail field carries a submitted name otherwise. The throttle tables keep submitted names in memory only. `test_audit.py` signs in with the real password typed as the username and `assert_not_logged` finds nothing. |

## 2. Should-fix (risk reviewer)

| ID | Finding | Answer |
|---|---|---|
| R3 | The audit vocabularies differ: DESIGN writes dotted events (`signin.throttled`, `user.disabled`) and outcome `ok`; UI.md translates and filters underscore codes (`signin_throttled`, `user_deactivated`) and `succeeded`/`failed`. | **Accepted.** DESIGN 10.2 is the one vocabulary, written as one table with explicit `event`, `outcome` and `detail` columns; UI.md 5.6 and the filter lists map exactly those codes to labels. A test compares the label map in `users.js` with the backend's event and outcome constants. |
| R4 | The gate is an `async` ASGI layer but 5.5 has it read the user record under `store.lock` (a threading lock held by `/api/logs` while it parses up to 20 MiB): every request and every terminal stalls, and the lock order between `store.lock` and the sessions lock is undefined (an ABBA deadlock risk). | **Accepted.** The gate takes no store lock and makes no blocking call. `Sessions` keeps a user index `{name: (role, disabled, password_changed, must_change_password)}` under its own lock, built at startup from the state and refreshed by every users route, setup, recovery and the own change (the route updates the index after its state save, inside `store.lock`). Setup mode is "the index is empty". Lock order: `store.lock` before the sessions lock, never the reverse; the sessions lock is never held across I/O. A test pins the order. |
| R5 (+U14) | The per-source throttle keys on the address and doubles to 15 min: a classroom behind one NAT is one source, and five failures from anyone there delay everyone. The fixed per-name delay counted from the last failure lets a distributed attacker keep a known name locked out (one failure every 30 s), the lockout 8.3 says cannot happen. | **Accepted with a new throttle model (DESIGN 8).** **L1, per (source key, name):** 5 free failures, then 30 s doubling to 15 min; a success for that pair clears it. **L2, per source key:** a sliding 15 min window of failure records; at 100 failures the source is delayed 30 s doubling to 15 min; a success for (S, N) removes only S's records for N, never the others. **L3, per name, for unfamiliar sources only:** a token bucket (10 tokens, one back every 30 s) that each failure from an unfamiliar source spends; empty → `429` for unfamiliar sources without hashing. A source is **familiar** for a name when its prefix (IPv4 /24, IPv6 /64) signed in successfully as that name before: the record keeps the last 8 such prefixes in a private `known_sources` list (never in `public_user`), so an attacker cannot lock a person out of the network they use, and a classroom NAT is one familiar prefix. The accepted remainder: a person signing in from a new network while their own name is under a distributed attack waits for a token; the audit log shows the attack. Every throttle check runs before any hashing. One sentence for every 429: *Too many sign-in attempts. Try again in {n} s.* Tests: 30 users behind one address with ordinary typos; one failure every 30 s against a name from fresh sources while the familiar source still signs in; the delay sequence of L1 and L2. |
| R6 | A success clears both counters, so an insider resets their per-source counter by signing in as themselves between guesses at the admin's password (2,880 guesses a day instead of about 96); an IPv6 host can rotate through its /64. | **Accepted** (in the R5 model): a success clears only the L1 pair and removes only its own records from L2. The source key is the IPv4 address, or the IPv6 /64; an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`, which is what IPv4 clients look like when `UI_BIND` is `::`) is unmapped first, so IPv4 clients never share the `::/64` bucket. The IPv6 part matters only when an operator binds an IPv6 address (the default `0.0.0.0` is IPv4 only). |
| R7 | The sign-in route is a `def` route in Starlette's shared pool of 40 threads; a fifth verify waits on the semaphore while holding a thread, so a sign-in flood holds every token and every `def` route hangs (measured: `/api/state` at 1.9 s under a burst of 120). | **Accepted.** The sign-in, setup and own-password routes are `async`. scrypt runs in a dedicated executor of 4 threads, never the shared pool; at most 16 verifies wait for it, beyond that the route answers `429 {code:'throttled', retry_after: 2}` without hashing. Every store read and write on these paths runs off the event loop (`run_in_threadpool`). Test: 50 concurrent sign-ins while `GET /api/state` answers within its normal time. |
| R8 | Scanners can rotate the audit trail away: every sign-in attempt is written twice (an `api.request` event and an audit entry), throttled ones cost the attacker nothing, and both files rotate at 5 MiB × 4. | **Accepted.** No `api.request` event for `POST /api/session` and `POST /api/setup`: their outcome is in the audit files only. Requests the gate refuses for lack of a valid session are logged nowhere (scanner noise); a session that expires is audited once (`session.expired`). DESIGN 6.1's "it is in the audit log" for gate refusals is corrected. `signin.failed`, `signin.throttled` and `setup.failed` go to their own file `audit-failures.jsonl` with its own rotation and are summed per source key per minute (one entry, `detail: count=<n>`), so a flood cannot push the security record (`setup`, `signin`, `signout`, `password.*`, `user.*`, `session.*`, `forbidden`, `manager.reset`) out of `audit.jsonl`. `GET /api/audit` reads both files and merges them by time. |
| R9 | The idle timeout never fires on a tab that stays on the Topology tab or keeps a drawer or a capture viewer open: their timer-driven GETs renew the session. | **Accepted, fail-closed.** A session renews only on acts of the person: a request with any method but GET and HEAD that passes the gate, a page navigation (GET or HEAD with `Accept: text/html`), and socket input (the terminal, console and capture handlers call `sessions.touch(id)` on client input, at most once a minute). No `GET /api/...` renews a session, so no poller can keep a tab signed in; the special list (`/api/state`, `/api/session`) goes. |
| R10 (+U10) | Sign-out both clears the capture owner cookie and promises that the same browser finds its desktop sessions again; if the cookie survived, the next person in that browser would inherit them. | **Accepted: sign-out ends this browser's capture sessions.** The refuters and the reviewers missed one fact: `clab_capture_owner` is set with `Path=/api/capture` (capture_sessions.py:113-114), so `DELETE /api/session` never receives it and cannot end the sessions itself. Sign-out is therefore two steps: `account.js` first calls the existing owner-scoped `POST /api/capture/sessions/end-all` (best effort; skipped when capture is disabled), then `DELETE /api/session`; and the `DELETE /api/session` response always clears `clab_capture_owner` with `Path=/api/capture`, so a later person in the same browser can never inherit a desktop session even when the first step failed (a session left by a failed first step ends at the capture service's own limit). Expiry ends nothing: the cookie stays, and the same browser signing in again finds its sessions. The sign-out item says so: *Signing out also closes this browser's Wireshark sessions.* |
| R11 (+U12) | Recovery prints `https://<address>/setup` with no port and no `?recover=1`, so it points at port 443 and the page shows the first-run wording; a person who types their own lost name hits a collision with no defined answer (and a builder could overwrite the existing record). | **Accepted.** `deploy/manager-recover-admin.sh` builds `https://<address>:<UI_PORT>/setup?recover=1` from `.env` exactly as `start-manager.sh` does and prints it after the code that `app.recover` prints. `setup.js` reads `?recover=1`: heading *Recovery: create one new administrator*, lead *Enter the code the recovery command printed, then choose a new administrator account. Existing accounts are not changed.* `POST /api/setup` never overwrites a record: an existing name answers `409 {code:'exists', message:'That name already exists. Choose a new name for the recovery administrator.'}`. DESIGN 9.5's "resets it or deletes the record" becomes "resets its password or deactivates it from People and sign-ins" (the page has no Delete, RECONCILIATION U-Q3). |
| R12 (+U17) | An admin who resets their own password through the users route ends their own session and lands in the restricted state; 3.2 and 7.3 disagree. | **Accepted.** `POST /api/users/{own name}/password` answers `409 {code:'self_change'}` with *Use Manager ▾ › Change password… for your own account.*; the own row's **Reset password…** is disabled with that caption; DESIGN 3.2's last bullet is rewritten to say so. |
| R13 (+U3) | An operator is sent into the admin-only VM connection dialog from six places, including an automatic prompt on first load, and every Save answers 403. | **Accepted.** `openVmDialog()` itself is role-aware: for an operator it shows *Ask an administrator to set up the VM connection.* instead of the form and sends nothing; `maybePromptVmConnection()` never opens for an operator; the Home banner for an operator reads *The lab VM is not connected yet. Ask an administrator to connect it.* A test calls every entry point as an operator and asserts that no `PUT /api/host` is sent. `vm-connection.html`'s Diagnostics sentence becomes role-neutral (an operator reaches that page only by typing its address). |
| R14 (+U6) | `login.js` never asks whether a session exists, so with `SameSite=Strict` every link from another site (a course page, an email) shows the sign-in form to a signed-in student. | **Accepted.** `login.js` asks `GET /api/session` once on load, with the form hidden behind *Checking…*: 200 → `next` (or the change view when restricted); 401 or a network failure → the form. A test in `test_login_ui.js`; the Playwright check starts from a cross-site navigation. |
| R15 | 92 regression and live tools under `docs/*/tools` drive the manager over HTTP without a session, many against `http://127.0.0.1:8081`; only `fixture_manager.py` was planned to change. | **Accepted, as its own build slice (BUILD.md S11).** (1) `fixture_manager.py` completes setup with fixture credentials and, by default, signs every request in through a fixture-only ASGI wrapper that adds the fixture admin's cookie when a request has none; `--signed-out` and `--role operator` switch it, and the sign-on checks use them. So the Playwright checks that run against the fixture keep working unchanged. Nothing of this is in `app/`. (2) A standard-library helper `docs/sign-on/tools/manager_http.py` for the live tools: an `https` base URL, `--cafile` or `--pin <cert.pem>`, credentials from `CLAB_USER` and `CLAB_PASSWORD` or a prompt (never a command-line value), and a cookie jar. (3) The live tools named in the routing table move to it (`docs/git-redesign/tools/live/*`, `integration/*`, `docs/multi-platform-restore/tools/*`). (4) `docs/sign-on/TOOLS.md` lists every tool that talks HTTP with its status: works through the fixture, migrated, or needs the helper (and why it was not migrated). |
| R16 | The health check silently loses its VM connection, topology browser and Git repository checks: `check_manager_routes` (`/api/discovery`, `/api/operations/browse`) and `check_git_route` (`/api/git/repositories`) sit behind the gate, and EXPOSURE 6.1 names neither. (The refuters corrected one part: the capture checks are covered by EXPOSURE 6.1.) | **Accepted; the lead's ruling E-Q2 is narrowed.** EXPOSURE 6.1 gains a table of every manager HTTP call in `check_install.py` with its new source. `GET /api/health` stays the only HTTP question the checker asks. Every other fact comes from `docker exec … python -m app.probe <name>`; a probe may **decrypt `state.enc` read-only** as `STORAGE_PROBE` already does (never constructs a `Store`, never writes, never logs a value), which serves the VM connection and discovery facts and the list of Git bindings. The end-to-end checks (`http-browse`, `git-http`) become probes that run the manager's own clients read-only from that state; where a probe cannot be built without a `Store`, the check stays and answers SKIP with the reason and *Open Manager ▾ › Diagnostics, which runs the same check.* None is dropped silently, and every matching `test_check_install.py` case is rewritten, never deleted. (EXPOSURE.md serves the Git side as a count of bound labs inside the `git-registry` probe: no check consumes the list itself.) |
| R17 | HSTS covers every port of a host (RFC 6797 8.3): with a provided certificate on a name, the browser rewrites `http://name:8081` to `https://name:8081`, so the redirect listener and any plain-HTTP lab service on that name break for 180 days. | **Accepted (documentation, an INFO and the upgrade table).** EXPOSURE 4.2, 7.4 and INSTALL.md state it: with a provided certificate, the 8081 redirect works by IP address or before the first HTTPS visit, and plain-HTTP lab services on that name are opened by IP. A health-check INFO under `tls.cert` in provided mode says it. |
| R18 | The certificate's addresses come from every interface, so docker0, every containerlab management bridge and link-local addresses go in, and a lab deploy changes the set: warnings and a regenerated certificate with a new fingerprint for every student. | **Accepted.** The certificate's IP names are the global-scope addresses of the default-route interface(s) plus the names and addresses the operator lists (`UI_ALLOWED_HOSTS`, `setup-tls.sh --name`); never `docker0`, `br-*`, `veth*`, `virbr*`, `cni*`, link-local or loopback. `ensure` never regenerates for an address outside that set. | R19 | The CLAUDE.md replacement drops "Never add a route or socket outside this", the DNS-rebinding sentence and "X-Forwarded-Host is never read"; the redirect is described three ways; the new security files have no routing rule. | **Accepted (the lead, at the release step).** The replacement keeps all three sentences, with the redirect named as the one exception. One redirect sentence everywhere: *`app/redirect.py` is the one listener outside the gate and the guard: it holds no data and answers 301 to the manager's own HTTPS origin after `host_allowed`, 400 for a refused Host or a request target that is not a path, 405 for any method but GET and HEAD, closes a socket 1008, and nothing else.* (The non-path refusal was added when EXPOSURE.md answered R20: h11 accepts a target such as `@evil.example/`, which would otherwise end up in `Location`.) The new files join `.claude/rules/routing-privileged-paths.md` once they exist (`test_path_globs_match_a_repository_file` refuses a glob without a file), and a "Sign-on, sessions, TLS" row joins the CLAUDE.md routing table. |

| R21 | The `/__fixture/expire` hook would put fixture-only code in the shipped app, gated by an environment variable, outside the route walk of `test_session.py`. | **Accepted** (in R15): the hook is a route of `fixture_manager.py` on the app it wraps, calling `app.state.sessions.end_user(name, reason)`. `app/` contains no fixture code. |
