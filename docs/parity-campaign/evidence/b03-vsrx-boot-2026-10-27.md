## 6. Direct SSH (`sshpass -p <published default> ssh admin@172.20.20.121`)

All exit 0.

- `show version | no-more`: `Hostname: vsrx`, `Model: vSRX`, **`Junos: 23.2R2.21`**, followed by about 55 `JUNOS ...` package lines (kernel `64-bit XEN [20240103.68b4802_builder_stable_12_232]`).
- `show interfaces terse | match "ge-|fxp"`: early (01:16): `fxp0 up up`, `fxp0.0 up up inet 10.0.0.15/24`. Later (01:17:33 and after): additionally `ge-0/0/0 up up`. The fxp0 address is the image's baked-in `10.0.0.15/24` and `2001:db8::2/64`, not the containerlab management address; SSH reaches the VM through the container's port forwarding.
- `show configuration security zones | display set | no-more`: **empty output** (no zones configured). `show security zones` lists only the built-in `junos-host` zone (0 interfaces bound).
- `show configuration system services | display set`: `set system services ssh root-login allow` and `set system services netconf ssh`.
- `show chassis hardware | match Chassis`: `Chassis  141495aa6d47  VSRX`.
- `show configuration | display set | match "interfaces|zones|login|services"` shows only the two `fxp0` address lines and the two services lines.

Serial console (port 5000):

- The requested `timeout 5 bash -c 'exec 3<>/dev/tcp/172.20.20.121/5000; head -c 200 <&3'` prints nothing and ends with exit 124, because `head -c 200` waits for 200 bytes. TCP connects.
- A Python socket probe shows the console answers: on connect it sends the telnet negotiation `ff fb 01 ff fb 03 ff fb 00 ff fd 00` (WILL ECHO, WILL SGA, WILL BINARY, DO BINARY); after a CR/LF it prints `FreeBSD/amd64 (vsrx) (ttyu0)` and `login: `. So a telnet-codec console works on 5000 (no credentials sent). `ss` inside the container shows no established connection on 5000 before the probe: the launcher closed its own.

Finding (healthcheck): the container reports **`unhealthy`** (FailingStreak growing, every probe `exec /healthcheck.py: exec format error`, exit 255) although `/health` contains `0 running`. `/healthcheck.py` starts with `import sys` and has no `#!` line, so Docker cannot exec it. Anything that trusts Docker's health status for vSRX will see it as never healthy; SSH readiness is the right signal.
